The encryption protecting VPN traffic today is safe against every computer that
currently exists. That's a weaker promise than it sounds: an attacker can record
your traffic now and decrypt it in ten years, once the machines catch up. If
what you're sending has to stay secret for a decade, the deadline has already
passed.

This is my BSc thesis. It runs ML-KEM-768 alongside WireGuard's existing X25519
handshake, on top of Cloudflare's BoringTun. *Hybrid* is the important word here:
ML-KEM is young, and young cryptography sometimes breaks, so I kept the old
handshake underneath it. An attacker has to defeat both, which means adopting it
early can't cost you the security you already had.

As far as I can tell it's the first FIPS 203-compliant hybrid WireGuard on a
production Rust codebase. I benchmarked it end to end on an Apple M4 and a
Raspberry Pi 5, because whether post-quantum cryptography works is settled.
What I wanted to know is what it costs on hardware people actually own.

## How it works

A WireGuard tunnel opens with two messages: an initiation and a response. The
hybrid version has the initiator generate a fresh ML-KEM-768 key pair alongside
its usual X25519 key and send the 1,184-byte public half in the initiation. The
responder encapsulates a secret against it and returns the 1,088-byte
ciphertext in the response, and the initiator decapsulates it. That's still a
single round trip.

Both sides then feed every secret, the four from X25519 and the one from
ML-KEM, through the same chain of HMAC-BLAKE2s steps that WireGuard already
uses, and derive the session key from the end of it. The key depends on all of
them, so it stays safe as long as either X25519 or ML-KEM holds, and because
the ML-KEM key pair is new for every handshake, every session is protected on
its own.

The thesis also measures a lighter alternative: using a one-time ML-KEM
exchange to fill WireGuard's existing pre-shared-key slot. It costs nothing
per handshake and changes nothing on the wire, but the key never changes, so
it gives up the per-session protection. The benchmarks put the two side by side.

The code went through the same scrutiny as the numbers. The post-quantum part
of the handshake is domain-separated, which closed a downgrade denial-of-service
an earlier version allowed, the secret decapsulation key is wiped from memory
after use, and tests check that tampered messages are rejected. For the thesis
defense I built a live demo that runs all three variants against a remote
server, captures each handshake as it happens, and sends a file through every
tunnel to show that only the handshake changes.

## What it costs

Less than you'd think. A handshake takes about 97 microseconds longer on the
M4 and 331 longer on the Pi, and on either machine that's dwarfed by the
network round trip it sits inside. The handshake messages grow from 148 and 92
bytes to 1,332 and 1,180, but each still fits in a single packet, so there's
no extra round trip and nothing to fragment. Once the tunnel is up the data
plane is untouched, throughput is the same as before, and a running peer uses
about 160 KB more memory.
